# CI 与发布验收门禁

## 背景

订单系统已经包含事务、异步消息、数据库适配器、认证、后台 Worker、Prometheus
规则和容器运行材料。只在本地手工执行检查，无法保证每次提交都重复执行同一套
验证，也无法及时发现 Dockerfile 或观测配置已经不能交付。

## 备选方案

1. 只依赖开发者本地执行 `make check`。
2. 只在 CI 中运行 Go 单元测试。
3. 在 CI 中分层执行 Go 代码检查、观测配置检查和容器构建，但不自动部署。

## 最终决定

采用第三种方案。每次推送到 `main` 或创建 Pull Request 时，CI 执行：

- `gofmt` 格式检查；
- 普通测试、race detector 和 `go vet`；
- Prometheus 配置、告警规则和 Tempo 配置校验；
- Docker 镜像构建。

本地使用 `make ci` 执行与 CI 等价的代码和观测门禁。容器构建在 CI 工作流中单独
执行，并依赖前面的 Go 与观测检查通过。

CI 不执行生产部署、不推送镜像、不修改数据库，也不把外部依赖的集成测试伪装成
默认单元测试。需要 PostgreSQL、Redis 或 Kafka 的检查仍通过明确的本地命令或后续
专用环境执行。

## 选择原因

- 分层失败可以快速区分代码、观测配置和容器交付问题；
- race detector 能覆盖 Go 并发代码中普通测试不一定触发的竞态；
- 容器构建可以提前发现编译入口、运行用户和构建上下文问题；
- 不自动部署，保留检查、发布和上线之间的独立授权边界。

## 影响和遗留风险

- CI 仍然依赖 GitHub Runner 的网络、Docker 和第三方 Action 可用性；
- 默认门禁没有连接真实 PostgreSQL、Redis、Kafka 集群，外部依赖集成测试仍需单独
  启动基础设施后执行；
- 通过 CI 只代表代码达到发布候选条件，不代表已经完成容量、灰度和回滚验收。

## 重新评估条件

- 增加真实数据库或消息队列的自动化集成环境时，应将对应检查加入独立 CI Job；
- 建立镜像仓库和部署平台后，再增加镜像签名、漏洞扫描和人工审批后的发布 Job；
- 生产 SLO 或合规要求变化时，重新评估门禁顺序和失败策略。
