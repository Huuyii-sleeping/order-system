# 0006：使用 Transactional Outbox 可靠发布订单事件

## 背景

创建订单后，通知、支付或数据分析模块可能需要异步获知订单事件。如果数据库
事务提交后再直接发送消息，进程可能在两步之间崩溃，导致订单存在但消息永久
丢失；如果先发送消息再提交事务，数据库回滚时又会产生不存在的订单事件。

## 决策

- 创建订单、扣减库存和写入 `orders.created.v1` Outbox 事件位于同一个事务。
  三者全部成功才提交，任何一步失败都整体回滚。
- 后台 Worker 定时认领到期消息。PostgreSQL 使用
  `FOR UPDATE SKIP LOCKED`，允许多个实例并发处理不同消息。
- 认领会写入唯一租约和过期时间。发布结果只能由持有当前租约的 Worker 确认，
  超时 Worker 不能覆盖后来 Worker 的状态。
- 发布失败会释放租约，并按照有最大值的指数退避设置下次处理时间。成功后保留
  已发布记录，便于审计和排障。
- 发布器通过 `Publisher` 端口接入。默认 `direct` 模式用于快速本地运行；需要
  跨进程持久化消息时使用 Kafka 协议适配器，订单事务和 Outbox Worker 不变。

## 投递语义和边界

该方案提供至少一次投递，而不是恰好一次。消息系统已经接收事件，但应用还没来
得及标记 `published_at` 就崩溃时，租约过期后仍会重新发布。消费者必须持久化
处理过的消息 ID，并把“检查消息 ID + 修改业务数据”放在同一个本地事务中。

Outbox 解决数据库与消息发布之间的一致性，不保证跨服务全局事务，也不自动处理
业务补偿。生产环境还需要监控积压数量、最老未发布事件年龄、重试次数，并制定
长期失败消息的处理策略。
