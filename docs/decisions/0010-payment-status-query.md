# 0010：通过独立查询用例暴露异步支付状态

## 背景

订单创建通过 Outbox 和消息消费者异步产生支付，再由 Payment Worker 调用第三方。
创建订单接口无法在响应时承诺支付已经结束，客户端需要一个明确入口观察最终结果。

订单状态和支付状态属于两个不同的业务概念。直接在 Payment Worker 中同步修改订单
虽然简单，但会让支付模块依赖订单存储，还会提前引入支付失败后的库存释放、重复事件
和跨模块事务等问题。

## 决策

- 新增 `GET /orders/{orderID}/payment`，返回订单对应支付的公开状态、金额和时间。
- HTTP 层只依赖 `PaymentQueries`，应用层的 `QueryService` 只依赖最小 `QueryStore`；
  消息 Consumer、任务 Worker 和 HTTP 查询不互相调用，只共享同一持久化状态。
- 查询必须同时使用 `order_id` 和认证上下文中的 `customer_id`。不存在和无权访问都
  返回 404，避免通过响应差异枚举其他用户的支付。
- 响应不暴露 `provider_reference` 和 `failure_reason`。前者属于内部对账标识，后者可能
  包含第三方诊断信息；将来应设计稳定、可公开的失败码，而不是直接泄露原始原因。
- 订单刚创建而消息尚未消费时，支付不存在是异步流程的正常中间状态，返回 404；
  客户端应使用有上限的退避轮询，而不是把它解释为订单创建失败。

## 状态语义

```text
订单创建成功
  -> 支付尚不存在
  -> pending
  -> processing
  -> succeeded | failed
                 \-> unknown -> processing（重试）
```

这里查询的是 Payment 聚合，而不是用 Order 状态推测支付结果。两个状态机暂时独立，
因此支付成功后订单仍可能是 `pending`。

## 边界和后续

下一阶段应通过显式的流程管理器或支付结果事件协调订单确认、支付失败取消和库存释放。
这属于跨聚合最终一致性问题，不应隐藏在查询接口或 Payment Store 中。本节没有实现
支付回调、对账、人工补偿或支付失败码映射。
