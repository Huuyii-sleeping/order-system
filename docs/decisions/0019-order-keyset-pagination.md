# 0019：订单历史使用复合游标分页

## 背景

订单列表会持续增长，不能一次返回全部数据。传统 `LIMIT + OFFSET` 容易理解，但页码越深，数据库需要跳过的记录越多；同时有新订单插入时，相邻两次请求还可能重复或漏掉记录。

订单的 `created_at` 也不是唯一值。如果只把时间放进游标，同一时刻创建的多笔订单无法形成唯一边界。

## 决定

- 提供 `GET /orders?limit=20&cursor=<opaque>`。用户身份只从认证 Context 取得，客户端不能指定 `customer_id`。
- 使用 `(created_at DESC, id DESC)` 作为稳定且唯一的排序组合。下一页查询条件是 `(created_at, id) < ($cursorCreatedAt, $cursorID)`。
- 应用层把版本、创建时间和订单 ID 编码成 Base64 URL-safe 游标，并负责严格解码和校验。HTTP 层和客户端只传递不透明字符串；数据库适配器只接收结构化边界。
- 默认每页 20 条，最多 100 条。存储层读取 `limit + 1` 条：额外一条只用于判断是否生成 `next_cursor`，不返回给客户端，也不执行额外的计数查询。
- PostgreSQL 使用 `(customer_id, created_at DESC, id DESC)` 复合索引，使租户过滤、排序和游标范围查询与同一个索引前缀一致。内存适配器实现相同的排序和边界语义。
- 空结果和最后一页返回空字符串 `next_cursor`；非法 limit 或 cursor 返回 400。

## 选择原因

Keyset Pagination 的查询成本不随页码线性增加。复合游标为相同创建时间的订单提供确定顺序，因此翻页时不会因为边界值相同而漏单或重复。

游标是查询位置，不是授权凭据。本实现没有签名或加密它：即使客户端修改边界，数据库查询仍强制使用认证用户的 `customer_id`，只能改变自己订单历史的起始位置，不能越权，也不能突破每页上限。若未来游标携带敏感筛选条件、租户身份或计费信息，应增加 HMAC 签名或服务端游标存储。

## 影响和边界

- 这是向后翻页接口，不支持跳到任意页，也不返回昂贵的实时总数。需要页码跳转或复杂搜索时应设计独立读模型。
- 翻页过程不是数据库快照。第一页之后新插入且排序更靠前的订单不会出现在本轮后续页面中；这通常符合“继续向历史读取”的用户预期。若要求全程一致快照，需要快照版本或物化结果，成本更高。
- 订单状态可能在翻页期间变化，但排序键不会变化，因此不会因状态更新而改变分页位置。
- Base64 只是不透明编码，不提供保密或防篡改能力。客户端不得解析并依赖内部字段；版本字段用于未来拒绝不兼容格式。
- 复合索引增加写入和存储成本。只有真实查询需要时才添加，查询形状变化后应重新检查 `EXPLAIN` 和索引使用情况。
