# 数据库连接池预算与背压观测

## 背景

Go 的 `sql.DB` 不是一条固定连接，而是一个并发安全的连接池。应用原本已经限制单进程最多打开
20 条连接，但参数写死在 PostgreSQL 适配器中，也没有暴露连接使用和等待情况。这会带来两个
问题：

- 扩容应用实例时，每个实例都会创建自己的连接池，数据库看到的理论连接上限会随实例数相乘；
- 接口变慢时，无法区分是 SQL 本身慢，还是连接池已耗尽、请求仍在等待可用连接。

连接池满时，`database/sql` 不会继续无限创建连接，而是让后续 `QueryContext`、`ExecContext`
和事务开启操作等待已有连接归还。这是一种本地背压，但等待仍会占用请求和 Worker 的执行预算；
如果调用方 Context 没有合理截止时间，请求可能长时间堆积。

## 决定

- 继续使用 `database/sql` 和 pgx 标准库驱动，不额外引入另一套连接池；
- 将单实例连接预算变成启动配置，并在启动时拒绝非正数以及空闲上限大于打开上限的配置：

  ```text
  DATABASE_MAX_OPEN_CONNS=20
  DATABASE_MAX_IDLE_CONNS=5
  DATABASE_CONN_MAX_LIFETIME=30m
  DATABASE_CONN_MAX_IDLE_TIME=5m
  ```

- `postgres.Open()` 保留给既有调用方，并使用默认值；应用组装使用 `OpenWithOptions()` 显式传入配置；
- 每次 Prometheus 抓取 `/metrics` 时直接读取 `sql.DBStats` 快照，不启动额外采集 goroutine；
- 指标只使用固定、低基数标签，暴露打开、使用中、空闲、最大连接数、累计等待次数、累计等待时长
  和连接回收原因；
- 只有“使用中连接达到上限的 90%”和“等待次数仍在增长”同时持续五分钟才告警，避免把短暂繁忙
  或预留较小误报为故障；
- 单实例最大连接数必须按数据库总容量倒推，而不是让每个实例各自取数据库允许的全部连接：

  ```text
  单实例 MaxOpenConns <= (数据库连接上限 - 运维与其他服务预留) / 最大应用实例数
  ```

## 参数含义

- `MaxOpenConns`：单实例打开连接的硬上限；池满时新调用等待，形成背压；
- `MaxIdleConns`：允许保留的空闲连接数，用连接复用换取更低的建连开销；
- `ConnMaxLifetime`：一条连接从创建起最多复用多久，用于周期性替换老连接；
- `ConnMaxIdleTime`：空闲连接最多保留多久，避免低流量实例长期占用数据库连接。

连接生命周期参数用于回收和轮换，不等于 SQL 执行超时。查询、事务和 Provider 调用仍应使用各自
的 Context 截止时间。

## 为什么连接池不是业务限流器

连接池只限制“同时占用数据库连接”的数量。大量 HTTP 请求仍然可以进入应用，然后一起等待
连接；已经取得连接的慢 SQL 或长事务也可能持续占用池。业务限流、Worker 并发、数据库连接池
和数据库自身容量保护位于不同层次，需要共同工作，不能互相替代。

## 影响和边界

- PostgreSQL 模式会导出连接池指标；内存模式没有数据库池，因此不会出现这些时间序列；
- 降低 `MaxOpenConns` 可以保护数据库，但过低会增加等待；盲目调高只能把排队位置从应用转移到
  数据库，并可能耗尽数据库全局连接；
- `WaitCount` 是进程生命周期内累计值，判断当前是否仍在等待必须使用 `rate()` 或 `increase()`；
- 指标只能证明连接池表现，不能定位慢 SQL、锁等待或数据库 CPU/IO 根因，仍需结合数据库侧观测；
- 当前没有引入独立连接代理。多实例的全局预算通过部署配置和容量计算约束。

## 重新评估条件

- 实例弹性范围很大、直接连接频繁抖动或数据库连接成本成为瓶颈时，评估 PgBouncer 等连接代理；
- 不同请求类型互相争抢同一连接池并造成关键链路饥饿时，评估拆库、独立池或更细的工作负载隔离；
- 告警稳定触发时，先定位慢查询、锁等待和长事务，再根据数据库容量与实测结果调整连接预算；
- 引入只读副本时，分别配置和观测读写连接池，不能把两个池当成同一份预算。
