# 事件契约测试与版本化边界

## 背景

订单、支付和通知目前运行在同一个模块化单体中，但它们已经通过 Outbox、消息 Topic 和 JSON
事件协作。进程内一起编译会掩盖一个问题：生产者修改字段后，未来独立部署的消费者可能无法
解析旧消息，或者意外收到支付渠道的内部敏感字段。

消息一旦写入 Broker，就可能在很长时间内被重放、延迟消费或由旧版本消费者读取。因此事件
结构不能只依赖当前 Go 类型编译通过，还需要一组针对实际 JSON 边界的契约测试。

## 决定

- 事件 Topic 和 Go 类型都带有明确版本，例如 `orders.created.v1` 与 `OrderCreatedV1`；
- `tests/contract` 对每个公开事件检查 Topic、JSON 字段集合和关键字段值；
- 允许消费者忽略新增的未知字段，新增字段属于需要评估的兼容性变化；
- 删除字段、改变字段含义、改变类型或改变必需语义时，不修改 v1，而是新增 v2 Topic 和类型；
- 支付结果事件只暴露订单侧推进流程所需的稳定字段，不暴露 Provider reference、原始响应或渠道失败细节；
- 契约测试不连接 Kafka，也不宣称已经验证 Schema Registry；它验证的是代码当前生成的公开 JSON 边界；
- `make contract-check` 作为独立门禁运行，同时纳入 `make ci` 和 GitHub Actions。

## 兼容变化示例

```text
增加可选字段             → 旧消费者通常可以忽略，但要更新契约评审
删除字段                 → 破坏性变化，新增 v2
string 改成 number       → 破坏性变化，新增 v2
改变字段含义             → 破坏性变化，新增 v2
把 Provider 原始信息加入事件 → 泄露内部契约，禁止直接加入
```

消费者仍然需要自己的业务校验。JSON 解码成功不代表订单 ID、金额、数量和事件类型一定符合
业务规则；契约测试解决“消息形状稳定”，消费者测试解决“业务处理正确”。

## 影响和边界

- 当前事件使用 JSON，字段测试是轻量且可读的；生产环境可以根据跨团队需要引入 Protobuf、Avro
  或 Schema Registry，但不能只因为有工具就跳过兼容性评审；
- 测试固定字段集合会在事件发生变化时主动失败，提醒开发者明确决定是更新 v1 还是创建 v2；
- 契约测试不能证明 Broker 投递、Outbox 事务、Inbox 幂等或消费者重试正确，这些仍由对应的集成和用例测试负责；
- 同一进程内的包引用不是服务边界证明，未来拆服务时仍应把事件当成公开协议维护。

## 重新评估条件

- 出现第二个独立语言的消费者时，增加跨语言 fixture 或 Schema Registry 兼容性检查；
- 事件数量和团队数量增加时，建立集中式 schema owner、兼容性策略和废弃周期；
- 事件包含敏感信息或需要加密时，单独设计字段脱敏、访问权限和密钥轮换，不把安全责任交给 JSON。
