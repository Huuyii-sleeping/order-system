# 向前迁移、备份恢复与发布回滚

## 背景

数据库结构和业务数据比单个应用版本存活更久。应用镜像可以快速回滚，但数据库在新版本
运行期间可能已经收到新写入，直接执行 `down migration` 或恢复旧备份可能删除结构和
覆盖新数据。另一方面，只验证 `pg_dump` 成功并不能证明备份真的可以恢复。

现有迁移器已经在事务内取得 PostgreSQL advisory lock，能够串行化多个迁移进程；但
`schema_migrations` 原本只记录版本和文件名，已经应用的 SQL 被修改后会静默跳过。

## 最终决定

- 迁移文件采用 forward-only：已应用文件不可修改、重命名或复用版本号；修正必须新增
  更高版本迁移；
- `schema_migrations` 保存文件名和 SHA-256 checksum。迁移器每次运行都校验历史文件，
  检测到漂移立即失败；
- 旧数据库第一次使用新迁移器时，为历史记录补齐当前文件的 checksum 基线，之后执行
  `NOT NULL` 约束；
- 继续使用事务级 advisory lock，保证多个迁移进程串行执行；
- 数据库变更使用 Expand/Contract：先添加向后兼容结构，再发布和回填，确认旧版本不再
  使用后，隔至少一个发布周期删除旧结构；
- 应用回滚默认保留已经成功执行的兼容数据库迁移，只回滚应用镜像；
- 数据损坏恢复到新数据库，验证迁移元数据和业务数据后再决定切换，不直接覆盖仍在接受
  写入的源数据库；
- CI 使用真实 PostgreSQL 执行 `pg_dump`、`pg_restore`、当前迁移器复验和业务数据指纹
  对比，证明备份可恢复。

## 为什么不默认提供 down migration

结构回退不等于业务回退。例如删除新列无法自动还原列中的数据；恢复旧备份还会丢失备份
之后的新订单。生产故障中更安全的优先顺序通常是：

1. 停止或摘除故障版本；
2. 在向后兼容的数据库结构上回滚应用；
3. 使用新的 forward migration 修复结构；
4. 只有数据已经损坏时，才进入停止写入、时间点恢复和数据对账流程。

## 影响和遗留风险

- 第一次为旧记录建立 checksum 基线时，无法证明这些文件在历史上从未被修改；保护从建立
  基线后开始生效；
- 当前迁移器把本次待执行迁移放在一个事务中，不支持必须位于事务外的
  `CREATE INDEX CONCURRENTLY`；大表在线变更需要独立工具或专用迁移模式；
- 本地恢复验收验证逻辑备份，不替代云数据库时间点恢复、跨区域副本和真实恢复时间目标
  演练；
- Expand/Contract 需要应用代码在过渡期同时兼容新旧结构，不能只靠迁移器自动保证。

## 重新评估条件

- 表规模使 DDL 锁或事务时间不可接受时，引入在线 schema change 工具；
- 建立生产数据库后，定义并定期演练 RPO、RTO、PITR 和跨区域恢复；
- 多个服务共同拥有同一数据库时，迁移所有权必须收敛到单一发布单元。
