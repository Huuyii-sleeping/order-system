# ADR 0039：API 版本使用并行入口和可观测迁移

## 背景

直接把 `/orders` 改成 `/api/v1/orders` 会立即破坏旧客户端；永远保留无版本路径又会让未来的
破坏性升级没有清晰边界。仅增加一个新路径也不够：如果不知道旧入口还有多少流量，就无法安全
判断何时可以删除它。

## 决策

1. `/api/v1` 是业务 HTTP API 的规范入口。健康检查、就绪检查、OpenAPI 和 Prometheus 仍是
   不带业务版本的运维协议。
2. 旧的无版本业务路径暂时继续调用同一套 Handler，不复制应用或领域逻辑。它返回：
   - `API-Version: v1`；
   - RFC 9745 `Deprecation` 日期；
   - 指向对应 `/api/v1/...` 路径的 `Link: rel="successor-version"`。
3. 新旧入口分别累计 `order_system_http_api_access_total{version="v1",entrypoint="..."}`。旧入口
   只有在调用方清单完成迁移、指标跨过约定观察窗口保持为零后才可删除。
4. Refresh Token Cookie 按入口限定为 `/auth` 或 `/api/v1/auth`。退出时同时清除两个 Path，避免
   迁移期间遗留可用凭证。
5. OpenAPI 把 `/api/v1` 放在第一个 Server，并保留旧 Server 的弃用说明。契约测试同时探测规范
   v1 和兼容入口。
6. 不设置虚假的 `Sunset`。只有负责人、调用方和发布日期达成一致后，才能公布不可逆的下线日期。

## 破坏性变化

v1 可以增加客户端可忽略的可选字段，但不能原地删除/重命名字段、改变类型或语义、增加必填输入、
改变认证方式或复用稳定错误码表达新含义。出现这些需求时应新增 v2，并按同样方式并行运行：

```text
v1 Handler/DTO  ──┐
                  ├── 同一应用用例与领域模型
v2 Handler/DTO  ──┘
```

版本边界位于传输契约，不等于复制 Service、Repository 或数据库。

## 影响与边界

- 两个入口在迁移期都会占用路由和测试成本，这是兼容性的显式成本。
- `Deprecation` 表示已经弃用，不等于已经承诺删除日期；`Sunset` 才表示停止服务时间。
- 入口流量归零只能证明近期没有观测到请求，还必须核对离线任务、低频调用方和灾备脚本。
- Webhook 回调地址也属于外部契约；Provider 完成配置切换前不能删除旧地址。
