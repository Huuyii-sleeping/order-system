# 0013：Redis 商品缓存与多实例共享限流

## 背景

商品详情是适合缓存的高频只读数据，但 PostgreSQL 仍然是商品事实来源。原有登录和刷新
限流只保存在单个 Go 进程内：部署两个实例后，同一客户端可以分别消耗两份额度，重启实例
也会清空计数。

## 决定

- Redis 是可选基础设施，由 `CACHE_DRIVER=redis` 显式启用。
- 只缓存商品详情，不缓存商品列表。详情采用 Cache Aside：先查 Redis，未命中再查事实仓库，
  成功后回填。正常结果使用有抖动的 TTL，降低大量 Key 同时过期造成的缓存雪崩。
- 不存在的商品写入短 TTL 的空值缓存，阻止相同无效 ID 持续穿透到数据库。
- 单个进程使用 `singleflight` 合并同一商品的并发回源，缓解热点 Key 失效时的缓存击穿。
  这不提供跨实例锁；不同实例仍可能各自回源一次。
- 商品缓存读写失败时 fail open：直接查询事实仓库，缓存故障不能改变商品查询结果。
- 创建订单不读取缓存，仍直接读取事实仓库，避免缓存旧价格进入订单。
- 登录和刷新固定窗口计数迁移到 Redis。Lua 脚本原子执行 `INCR` 和首次 `PEXPIRE`，
  多个实例共享同一配额。原始客户端地址先经过 SHA-256，再进入 Redis Key。
- 认证限流失败时 fail closed，返回 503；不能因 Redis 故障静默移除暴力破解保护。
- 启用 Redis 后将其纳入 readiness。缓存查询自身可以降级，但认证入口把它作为安全依赖。

## 原因

Cache Aside 保留了清晰的事实来源和简单的失败边界，适合当前只读商品目录。短空值缓存、
单实例请求合并和 TTL 抖动分别处理穿透、击穿和雪崩，它们解决的不是同一个问题。

共享限流必须依赖所有实例都能看到的原子状态。把计数留在进程内无法形成全局上限；把
`INCR` 和 `EXPIRE` 分成两个网络请求，又可能在中间崩溃后留下永不过期的 Key。

## 影响与边界

- 当前没有商品写接口，因此缓存一致性依赖 TTL。增加商品后台时，需要在数据库提交后删除
  详情 Key；删除失败仍可能在 TTL 内读到旧值。
- 空值缓存会让刚创建的同 ID 商品在短 TTL 内暂时不可见，这是防穿透换来的有界陈旧。
- `singleflight` 只合并当前进程内的并发请求。只有真实流量证明跨实例回源仍会压垮数据库时，
  才考虑分布式租约、逻辑过期或后台刷新，避免过早引入复杂锁。
- 固定窗口算法在窗口边界附近允许突发流量。需要更平滑的流量控制时，可改为令牌桶或滑动窗口。
- Redis 中的限流状态用于安全控制而非永久业务事实；AOF 只改善本地重启体验，不承诺零丢失。

## 重新评估条件

出现商品写入、价格实时变更、大规模热点、多个区域部署，或固定窗口的边界突发不可接受时，
重新评估缓存失效协议、跨实例击穿保护和限流算法。
