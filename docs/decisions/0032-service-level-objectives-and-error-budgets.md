# 0032：用 SLI、SLO 和错误预算定义 HTTP 可靠性

## 背景

项目已经能采集 HTTP 请求数、状态码和耗时，也有固定的 5xx 比例与 p95 延迟告警。但“指标存在”
不等于“可靠性目标明确”：5xx 达到多少才需要立即处理、偶发慢请求能否接受、短暂尖峰和持续故障
如何区分，都缺少统一判断标准。

固定阈值只描述某个时间窗口的现象，不能回答一段时间内允许失败多少，也不能帮助团队在稳定性和
功能迭代之间做取舍。因此需要从用户能够感知的行为出发定义 SLI，并用 SLO 和错误预算决定告警。

## 决定

本地学习基线定义两个 28 天滚动 HTTP SLO：

| SLO | Good event | Objective | Error budget |
| --- | --- | --- | --- |
| HTTP availability | 业务请求返回非 5xx | 99.9% | 0.1% |
| HTTP latency | 业务请求在 500ms 内完成 | 99% | 1% |

业务请求排除 `/healthz`、`/readyz` 和 `/metrics`。这些高频机器请求不能稀释真实业务失败率；目标
抓取失败继续由 `OrderSystemTargetDown` 独立告警。

HTTP 4xx 表示应用完成了认证、参数校验、限流或业务拒绝，本阶段不把它计为 availability 的 bad
event。延迟 SLO 则观察所有符合条件的业务请求，不论最终状态码。

Prometheus 记录 5m、30m、1h 和 6h 的错误比例。错误预算燃烧率定义为：

```text
burn rate = observed bad-event ratio / allowed bad-event ratio
```

`1x` 表示继续保持当前失败比例会刚好在 28 天用完预算。告警使用长短窗口同时判断：

| Alert | Long window | Short window | Burn rate | Approximate budget impact |
| --- | --- | --- | --- | --- |
| fast / critical | 1h | 5m | 14.4x | 一小时约消耗 2% 预算 |
| slow / warning | 6h | 30m | 6x | 六小时约消耗 5% 预算 |

长窗口避免单点抖动，短窗口确认故障此刻仍在持续。因为双窗口已经承担持续性判断，SLO 告警不再
额外增加 `for`。本地低流量服务还设置最低流量门槛：fast 使用 0.1 requests/s，slow 使用
0.05 requests/s，避免一个失败请求直接产生值班告警；SLI 和错误预算计算本身不受门槛影响。

原有固定 HTTP 5xx 与 p95 告警由燃烧率告警替代。p95 图表继续保留用于诊断，但不再作为唯一的
用户可靠性判据。

## 为什么这样选择

- SLI 直接描述用户成功和速度，不依赖某个内部组件是否“看起来健康”；
- 错误预算把 99.9% 转换成可计算的失败额度，允许合理故障而不是追求无法兑现的 100%；
- 多窗口燃烧率同时覆盖突然的大故障和较慢的持续退化，比单一 5 分钟阈值更少噪声；
- Recording Rule 复用同一套 PromQL，避免 Dashboard 与 Alert 各自复制并逐渐产生不同口径；
- 规则测试用合成时间序列验证目标流量、探针排除、快慢燃烧与低流量静默。

## 影响和边界

- 99.9% 和 99% 是学习基线，不是未经业务评审即可对外承诺的 SLA；
- 应用指标看不到 DNS、TLS、入口网关或请求未到达进程的故障。生产环境应优先使用网关或外部探测
  指标定义用户 SLI，并用应用指标诊断根因；
- 抓取中断时无法继续计算应用侧 SLI，因此 TargetDown 不能被 SLO 告警替代；
- 把所有 4xx 视为 availability good event 是当前口径。若产品把 429、鉴权故障或特定业务拒绝
  视为不可用，需要拆分状态或业务结果指标；
- 本地 Prometheus 保留 30 天数据以覆盖 28 天窗口，但重建数据卷、应用未运行和抓取缺口都会让
  本地结果不具备生产合规证明；
- 低流量门槛可能让真实但样本很少的故障不触发 SLO 告警，低流量关键业务还应增加合成探测或
  单事件告警；
- SLO 只能说明用户影响程度，不能取代 Kafka Lag、数据库池饱和或 Provider 熔断等根因告警。

## 重新评估条件

- 产品明确哪些接口、用户等级或地区属于独立服务承诺时，按服务边界拆分 SLI；
- 有稳定入口层指标或外部合成探测后，将 SLO 数据源从单实例应用指标迁移到用户入口；
- 正常流量、请求耗时或值班策略发生变化时，重新评审目标、延迟阈值和最低流量门槛；
- 需要正式 SLA 或季度可靠性报告时，引入具备长期保留、缺失数据处理和变更审计的 SLO 平台。
