# ADR 0036：用查询计划和数据量回归保护数据库访问

## 背景

单元测试可以证明订单列表返回正确的记录，但不能证明 PostgreSQL 会用合适的执行计划。
数据量变大、统计信息过期、过滤条件或排序字段变化后，一条仍然“正确”的 SQL 可能退化为
全表扫描，或者在应用循环中变成 N+1 次查询。Keyset Pagination 也只有在查询谓词、排序和
复合索引保持同一个形状时，才能稳定地从游标位置继续读取。

## 决策

1. 订单历史继续使用 `(customer_id, created_at DESC, id DESC)` 复合索引，查询必须同时包含
   用户隔离条件、游标边界和相同顺序的 `ORDER BY`。
2. PostgreSQL 集成测试增加一个接近真实基数的执行计划回归：在独立 schema 中写入 5,000
   条订单，执行 `ANALYZE`，再用 `EXPLAIN (FORMAT JSON)` 检查目标索引被使用且没有 `Seq Scan`。
3. 计划回归只断言结构性事实（目标索引、节点类型），不把本地容器的毫秒数或 cost 数字写死。
   这些数值会受到 CPU、缓存、统计信息和数据分布影响。
4. N+1 不是“多加一个索引”就能解决的问题。发现列表循环逐条调用 `GetByID` 时，先通过
   Trace、数据库查询计数或受控的 `pg_stat_statements` 证明确实存在重复查询，再改成批量查询、
   Join 或 Data Loader，并保留结果等价测试。

## 为什么这样做

- `EXPLAIN` 不执行查询，适合在验收中检查规划器选择；生产排障需要谨慎使用带
  `ANALYZE` 的版本，因为它会真实执行 SQL。
- 只检查“用了某个索引”还不够，`Seq Scan` 说明数据访问规模可能随表增长线性放大；两者结合
  才能固定本查询最重要的访问路径。
- 计划是 PostgreSQL 的运行时决策，不是 Go 代码的静态属性，所以该检查放在真实 PostgreSQL
  集成测试中，而不是内存适配器或单元测试中。

## 影响与边界

- 这项检查不会保证所有数据分布下都永远使用同一个节点；统计信息和选择性变化时，规划器
  可能合理地切换计划。失败时应先查看数据分布、`ANALYZE` 状态和完整计划，而不是盲目强制
  `enable_seqscan`。
- 测试只覆盖订单历史这一条高频查询；新增列表、报表和批处理 SQL 时，应为它们单独定义
  查询形状、索引和验收证据。
- 生产环境不应把用户输入拼接进 `EXPLAIN`，也不应为了测试长期关闭顺序扫描。

## 重新评估条件

- 订单排序字段、租户隔离方式或游标协议发生变化。
- 订单规模、典型客户订单数或查询延迟 SLO 明显变化。
- 观测发现数据库 CPU、Buffer Read、慢查询或单请求 SQL 数量持续上升。
