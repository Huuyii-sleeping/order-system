# 0002：使用不透明 Token 和数据库会话

状态：已采用

## 背景

订单 API 不能相信客户端提交的 `customer_id`，否则调用者可以伪造其他用户
身份创建或读取订单。服务需要先认证调用者，再把可信身份传给订单用例。同时，
泄露数据库备份不应直接暴露可立即使用的登录凭证。

## 决策

- 注册时规范化邮箱，并使用 bcrypt 保存不可逆密码哈希。
- 登录成功后生成 256 位随机不透明 Token；原始 Token 只在登录响应中返回。
- 数据库只保存 Token 的 SHA-256 摘要、用户 ID 和过期时间。
- 认证中间件读取 `Authorization: Bearer ...`，查询有效会话并把用户 ID 写入
  Request Context。
- 订单 Handler 从 Context 取得用户 ID，不再接受请求体中的 `customer_id`。
- 查询订单时在存储查询条件中同时约束订单 ID 和用户 ID；其他用户看到的结果
  与订单不存在相同，避免泄露资源是否存在。
- 提供当前会话登出和用户全部会话登出；删除会话记录后 Token 立即失效。

## 为什么暂不使用 JWT

数据库会话的状态清晰，后续可以直接实现登出、主动撤销、设备管理和封禁。JWT
可减少每次请求的数据库查询，但撤销和密钥轮换更复杂；当前规模尚未证明需要这项
权衡。

## 结果与限制

认证与授权成为两个独立步骤：Token 回答“你是谁”，订单查询条件回答“你能访问
什么”。会话默认有效 24 小时。当前尚未实现刷新 Token、登录限流、邮箱验证和
过期会话清理任务，这些能力将在后续需求出现时补充。
