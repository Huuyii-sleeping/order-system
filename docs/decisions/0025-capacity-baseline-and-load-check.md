# 容量基线与压测验收

## 背景

单元测试和端到端测试可以验证功能正确，但不能回答服务在并发请求下是否仍然满足延迟、吞吐和错误率目标。
如果没有可重复的基线，调整连接池、缓存、Worker 并发或数据库索引时，就只能凭感觉判断性能变化。

当前项目已经具备 HTTP 指标、PostgreSQL、Redis 和真实基础设施验收，因此增加一个轻量、可重复的本地容量检查，
用于发现明显回归，而不是把本地机器的结果当作生产容量承诺。

## 决定

- 新增 `tests/load` 标准库 HTTP 压测程序，支持固定并发、持续时间、超时、RPS、错误率和 P95 阈值；
- `scripts/performance-check.sh` 在隔离 Compose Project 中启动完整 PostgreSQL、Redis、Redpanda 和 API，测量商品详情缓存读和 liveness 两条路径；
- 性能检查使用独立端口、数据卷和容器，并在结束后自动清理；
- 默认阈值只是本地学习基线：商品列表至少 50 RPS、P95 不超过 500ms，健康检查至少 100 RPS、P95 不超过 250ms，错误率不超过 1%；
- CI 将性能检查作为独立 Job，避免把吞吐数字混入普通单元测试；
- 不使用订单创建作为默认基线，因为订单写入会消耗库存、产生异步任务，且会受到模拟支付和消息调度的影响；写路径容量需要独立的、可重置数据集和业务场景。

## 为什么只使用固定并发

固定并发能够比较容易回答：在同时有 N 个请求时，服务的吞吐、延迟和错误率如何变化。
它不是完整的生产压测模型，也不模拟突发流量、长尾请求、跨区域网络和真实用户行为。

## 指标解释

- 吞吐：单位时间内完成的请求数，当前报告为 RPS；
- P50：一半请求不超过这个延迟；
- P95：95% 请求不超过这个延迟，适合观察大多数用户体验；
- P99：用于观察长尾，但对短时间本地测试更容易受调度噪声影响；
- 错误率：非 200 响应或请求错误占全部请求的比例。

## 影响和边界

- 结果受本机 CPU、Docker 资源、网络和运行时缓存影响，不代表生产 QPS；
- 应先固定测试时长、并发数、数据集和配置，再比较代码变更前后的趋势；
- 通过基线只说明没有明显回归，不能说明系统已经完成容量规划；
- 真正上线前仍需要根据 SLO 做阶梯压测、突发压测、长稳压测和数据库容量验证。

## 重新评估条件

- 增加写路径或支付链路容量目标时，建立可重复的业务数据重置和独立场景；
- 引入生产流量模型后，把固定并发检查升级为阶梯负载和分位数报告；
- 需要跨实例容量时，使用多 API 实例、独立压测机和真实的数据库连接池规模验证。
