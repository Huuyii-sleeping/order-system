# 0014：支付 Provider 的超时、舱壁与熔断

## 背景

Payment Worker 必须调用事务之外的第三方支付系统。下游变慢或不可用时，如果没有时间和
并发边界，Worker 会长期占用任务租约、goroutine、连接和内存；持续重试还会进一步打击
正在故障的下游。另一方面，调用失败或超时不能证明扣款没有发生，不能直接把支付标记为
`failed`。

## 决定

- Worker 认领一批任务后使用固定大小的 worker pool 并发处理，不为每条任务无限创建
  goroutine。
- 在具体 Provider 外包装一个仍实现应用层 `Provider` 端口的稳定性装饰器。每次调用有
  独立超时，并通过非阻塞 semaphore 限制本进程同时访问 Provider 的数量。
- 舱壁满时立即返回，让持久化 Payment Task 负责后续退避；不在内存中建立第二条等待队列。
- 连续依赖故障达到阈值后打开熔断器。冷却期内快速拒绝；到期后进入 `half_open`，只放行
  一个探测请求。探测成功关闭熔断，失败则重新打开。
- 成功与明确业务拒绝都证明 Provider 能正常响应，会重置连续故障；网络错误、调用超时和
  非法协议结果计入故障。调用方取消（例如进程关闭）不归咎于下游。
- 超时、舱壁拒绝、熔断拒绝和网络错误都由 Worker 保存为 `unknown`，使用任务创建时的
  稳定幂等键重试。明确业务拒绝才保存为 `failed`。
- 暴露低基数的调用结果、耗时、拒绝原因、熔断状态和状态切换指标；不把业务 ID 或错误
  文本用作 Prometheus 标签。
- 配置校验要求按批次并发度估算的最坏调用超时预算小于任务租约，减少处理尚未结束时被
  其他 Worker 重新认领的机会。

## 为什么放在 Provider 装饰器

超时、舱壁和熔断描述的是“如何安全访问一个外部依赖”，不是支付状态机本身。装饰器保持
`Provider` 接口不变，Worker 只需要理解成功、明确拒绝和不确定结果。将来从模块化单体拆成
支付微服务，调用方仍可复用这个边界；熔断状态默认按实例独立维护，不要求每个实例同步。

## 影响与边界

- 当前熔断算法使用连续失败阈值，适合学习和低流量场景。生产系统通常还需要滑动窗口、
  最小样本数、失败比例、慢调用比例和配置热更新。
- 快速拒绝是降级，不是支付失败。它减少资源消耗，但会增加支付完成延迟。
- Provider 必须遵守 Context 取消；否则 Go 无法强制终止已经进入第三方库的阻塞调用。真实
  HTTP Client 还应配置连接、TLS、响应头和空闲连接等分层超时。
- 本地模拟器支持延迟和前 N 次失败，只用于确定性故障演练。真实第三方状态仍需要回调、
  主动查询和对账流程确认。
- 当前并发上限是单进程上限。多实例部署后的总并发约等于实例数乘以单实例上限，仍需结合
  Provider 配额、全局限流、队列积压和自动扩缩容一起规划。
