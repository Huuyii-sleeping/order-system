# 0020：过期认证凭证清理与有界维护 Worker

## 背景

认证请求会在查询时排除过期的 Access Session，Refresh Token 也会在应用层判断有效期。
这能保证安全语义，但不会自动删除数据库中的历史记录。长期运行后，`sessions` 和
`refresh_tokens` 会持续膨胀，索引、备份和恢复时间也会随之增加。

## 方案

新增独立的认证凭证维护用例和后台 Worker：

1. 每次维护最多删除 `AUTH_CREDENTIAL_CLEANUP_BATCH_SIZE` 条过期 Session 和 Refresh Token。
2. PostgreSQL 使用 `expires_at` 索引先选出有限批次，再按主键删除；两张表在一个短事务中提交。
3. 服务启动后立即执行一批，之后按 `AUTH_CREDENTIAL_CLEANUP_INTERVAL` 周期执行。
4. 一次数据库错误只记录日志并等待下一轮，不让维护任务退出整个 API 进程。
5. Worker 的 `stopCtx` 停止未来批次，`workCtx` 只在关闭预算耗尽时取消当前 SQL 操作。

## 为什么不放在 HTTP Handler

清理与用户当前请求没有直接关系。把它放进 Handler 会让请求延迟、数据库写放大和维护
失败耦合在一起，也无法保证没有流量时仍然回收数据。独立 Worker 可以单独限速、重试、
观测和优雅关闭。

## 事务与批量边界

两张表在同一短事务中提交，避免一次维护批次只清理一张表就返回成功。批量上限则防止
历史积压导致单次 `DELETE` 持锁过久；如果数据量很大，Worker 会在后续周期继续清理。
这不是业务事务，不会改变用户、订单或凭证的有效性判断。

## 重新评估条件

- 单批次删除仍然超过数据库锁等待预算时，应进一步缩小批次或改成更细的分片任务。
- 需要跨多个服务统一清理时，应迁移到独立维护服务或平台级 Job，但仍保持数据库端有界删除。
- 需要容量告警时，可以在不带用户 ID 和 token hash 的前提下增加低基数删除计数与失败指标。
