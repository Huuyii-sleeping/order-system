# 0017：先查询对账，再重试不确定的通知

## 背景

通知 Provider 与本地 PostgreSQL 无法共享事务。Provider 可能已经发送成功，但响应在返回途中丢失；进程也可能在 Provider 成功后、提交本地结果前崩溃。此时本地通知会处于 `unknown`，或者任务租约过期但通知仍为 `processing`。直接再次发送会把“恢复状态”变成新的外部副作用，并把正确性完全押在 Provider 的幂等实现上。

## 决定

- Provider 端口同时提供 `Send` 和按稳定幂等键执行的 `Lookup`。
- 首次领取 `pending` 任务时直接发送；重新领取 `unknown` 或租约过期的 `processing` 任务时，必须先查询 Provider。
- 查询到明确结果时，Notification 直接收敛为 `sent` 或 `failed`，NotificationTask 同时完成，不再次发送。
- 查询返回未找到时，继续使用原幂等键发送；查询报错或超时时保持 `unknown` 并退避，禁止在结果仍不确定时继续发送。
- 数据库在认领任务时计算 `NeedsReconciliation`，它是本次执行的派生信息，不作为第二份持久化业务状态。
- Provider 查询和发送都在任务租约之外的数据库事务中执行；最终业务状态和任务状态仍在一个短事务中提交，并校验 `lease_id`。

## 选择原因

查询优先把“重复发送”降为“重复读取”，既能处理响应丢失，也能处理 Provider 成功后进程崩溃的窗口。稳定幂等键仍然保留，因为查询可能暂时返回未找到，或 Provider 的查询视图存在传播延迟；它是重发时的最后一道副作用保护。

## 影响和边界

- Provider 必须提供按幂等键查询的契约，并明确查询一致性、数据保留时间和终态含义。
- `not_found` 不等同于“从未执行”。真实 Provider 若为最终一致查询，应配置安全等待窗口；当前模拟 Provider 的查询是强一致的。
- 查询失败会延迟通知收敛，但不会在不确定状态下盲目发送。
- 当前只对通知链路实现自动对账；支付对账通常还需要账单、退款和人工审核等更严格流程，应单独设计。

## 重新评估条件

- Provider 通过回调或 Webhook 主动返回送达结果时；
- 查询接口是最终一致、限流严格或只保留短期数据，需要增加对账延迟、独立队列或人工工单时；
- 需要区分“Provider 接受”“渠道送达”和“用户已读”等多级业务状态时。
