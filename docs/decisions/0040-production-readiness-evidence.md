# ADR 0040：生产验收必须由可重复证据和外部签字共同组成

## 背景

“单元测试通过”只能证明有限输入下的代码行为；“E2E 通过”也不能证明备份可恢复、镜像以非 root
运行、性能达到基线或发布可以回滚。另一方面，本地脚本即使全部成功，也无法替代真实云资源、
外部 Provider、TLS、容量、合规和当班负责人确认。

## 决策

1. `make production-readiness-check` 作为本地发布候选总门禁，按顺序执行且失败即停止：
   - Go module checksum；
   - 格式、测试、Race、Vet、契约、可观测和 Kubernetes 清单检查；
   - release image 构建、非 root 用户与二进制检查；
   - PostgreSQL、Redis、Redpanda 和规范 `/api/v1` 的真实 E2E 与依赖故障演练；
   - migration、备份、全新数据库恢复与数据指纹；
   - 隔离环境性能基线；
   - 双实例 canary 和 rollback 冒烟。
2. 各基础设施门禁使用独立 Compose Project、端口、临时卷和合成数据，不读取或清理开发数据。
3. GitHub Actions 保留可并行的独立 Job，最终 `release-readiness` 只有在全部依赖门禁成功后才成功。
4. 自动矩阵通过的含义是“代码级发布候选证据齐全”，不是“已经批准生产发布”。真实环境签字项
   必须由负责人在发布记录中确认，不能在脚本中伪造。

## 影响与边界

- 总门禁耗时比单元测试长，适合发布候选和合并保护，不适合每次本地保存时运行。
- 本地性能阈值用于发现明显回退，不代表生产容量结论；生产容量需要同规格环境和真实流量模型。
- 本地备份恢复证明流程可执行，不证明生产备份保留、加密、跨区复制和 RPO/RTO 已达标。
- Kubernetes 目前只渲染和静态验证清单，没有证明真实集群的调度、网络、证书、扩缩容与权限正确。
