# 0007：使用 Inbox 和持久化任务处理支付

## 背景

Outbox 提供至少一次投递，同一条 `orders.created.v1` 事件可能到达消费者多次。
支付又依赖本地数据库和第三方系统，单个数据库事务无法覆盖第三方调用。

## 决策

- 支付消费者在同一个本地事务中写入 Inbox、创建 Payment 和 PaymentTask。
  `inbox_messages.message_id` 是唯一键，重复事件不会产生重复业务效果。
- Inbox 同时保存 Topic 和 Payload 哈希。同一个消息 ID 携带不同内容时返回冲突，
  避免把生产者错误误判成正常重试。
- Payment 使用 `pending`、`processing`、`succeeded`、`failed` 和 `unknown`
  状态机；领域对象限制非法状态转换。
- 第三方调用发生在本地数据库事务之外。PaymentTask 使用短数据库行锁完成认领，
  再使用带过期时间的租约保护调用期间的处理权。
- 所有第三方重试使用 Payment ID 作为稳定幂等键。超时表示结果未知，支付进入
  `unknown` 并重试；明确拒绝才进入 `failed`。
- 当前进程内消息适配器和模拟支付 Provider 只用于验证边界。以后替换 Kafka 和
  真实 Provider 时，不改变消费事务和支付状态机。

## 一致性边界

数据库事务只能保证本地状态原子提交，不能回滚已经发生的第三方调用。因此系统
依赖第三方幂等键来安全重试，并需要在生产实现中补充结果查询、Webhook 校验、
对账和人工处理。若第三方既不支持幂等也不支持查询，网络超时后无法同时保证
不重复和不丢失。
