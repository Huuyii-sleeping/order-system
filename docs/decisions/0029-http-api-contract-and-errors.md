# HTTP API 契约与稳定错误码

## 背景

Handler 已经会在每次请求到达时检查 Content-Type、JSON 结构、认证信息和业务输入，但这只能
回答“当前服务是否接受这次请求”。客户端仍然需要一份机器可读的说明来知道路由、参数、认证
方式、成功响应和错误响应；开发者也需要在修改字段或路由时得到兼容性提醒。

仅靠 Handler 单元测试也不够。测试可以证明代码按测试预期运行，却无法自动告诉客户端协议长
什么样，也无法保证新增接口时同步维护公开说明。反过来，只有一份手写 OpenAPI 而没有测试，
说明书也可能逐渐与真实路由分离。

原有错误响应只有 `error` 文案。文案适合人阅读，但客户端如果根据英文句子分支，改写一句提示
也会造成兼容性问题，因此需要稳定的机器错误码。

## 决定

- 使用 OpenAPI 3.1 JSON 描述 HTTP 契约，源文件位于 `api/openapi/spec.json`；
- 应用通过 `GET /openapi.json` 返回嵌入二进制的同一份文件，运行时没有第二套动态生成结果；
- `tests/contract/http_api_test.go` 固定路径、方法、`operationId`、安全边界、公开 JSON 字段和敏感字段边界；
- 契约测试还会用真实 Router 探测每一个文档化操作，防止文档声明了不存在的方法或路径；
- 错误响应增加稳定的 `code`，同时保留原来的 `error` 文案字段：

  ```json
  {
    "code": "payment_not_found",
    "error": "payment not found"
  }
  ```

- 客户端只根据 `code` 执行业务分支，`error` 只用于展示和诊断；
- 新增可选响应字段通常属于兼容变化，但仍要更新 OpenAPI 和契约测试；删除字段、重命名、改类型、
  改认证方式或改变字段含义属于破坏性变化，需要新的 API 版本或明确的迁移与废弃周期；
- `/metrics` 是 Prometheus 内部抓取协议，不属于面向业务客户端的 JSON API，不写入这份 OpenAPI。

## 三层职责

```text
Handler 运行时校验  →  拒绝这一次不合法请求
OpenAPI 文档         →  描述客户端可以依赖的 HTTP 协议
契约测试             →  在 CI 中阻止开发者无意改变协议或让文档脱离路由
```

OpenAPI 不是运行时输入校验器，契约测试也不代替 Handler 单元测试。三者保护的是不同时间点和
不同参与者。

## 兼容性示例

| 修改 | 兼容性判断 | 处理方式 |
| --- | --- | --- |
| 增加客户端可忽略的可选响应字段 | 通常兼容 | 更新 OpenAPI 和测试，评审隐私边界 |
| 增加必填请求字段 | 破坏旧客户端 | 新版本或分阶段迁移 |
| 删除或重命名响应字段 | 破坏旧客户端 | 新版本并保留旧版本过渡 |
| 改变字段类型或业务含义 | 破坏性 | 新字段或新版本，不复用旧名字 |
| 修改 `error` 展示文案 | 兼容 | `code` 保持不变 |
| 修改错误 `code` | 破坏客户端分支 | 新码兼容期或版本化 |

## 影响和边界

- 当前不引入代码生成器或外部 OpenAPI 校验库，契约使用标准 JSON，检查保持快速且离线；
- 路由探测只证明方法与路径已经注册，不证明每个真实依赖和业务流程都成功，完整链路仍由 E2E 验证；
- 成功响应字段由 OpenAPI 契约测试和 Handler 单元测试共同保护，但当前没有自动生成 SDK；
- OpenAPI 中的本地 Server 地址只用于示例，不代表生产域名或部署配置；
- 支付、通知等响应继续禁止暴露 Provider reference、失败原因和原始响应。

## 重新评估条件

- 出现独立前端或第三方调用方时，考虑从 OpenAPI 生成类型安全客户端并加入生成物一致性检查；
- API 数量显著增加时，引入完整 OpenAPI linter 和规范兼容性 diff 工具；
- 需要正式废弃旧接口时，增加版本生命周期、弃用 Header 和调用方迁移观测；
- 对外开放 API 时，补充网关鉴权、配额、审计、服务条款和更严格的错误信息披露策略。
