# 真实基础设施集成验收与故障演练

## 背景

单元测试可以验证领域规则和应用用例，却不能证明 PostgreSQL 的事务与锁、Redis 的
跨实例共享状态、Kafka 协议链路、容器组装和公开 HTTP API 能一起工作。仅仅把这些
依赖启动起来也不够：系统还必须在关键依赖故障时停止接收新流量，并在依赖恢复后
重新就绪。

## 备选方案

1. 继续依赖各适配器的单元测试和人工启动验证。
2. 在普通 `go test ./...` 中始终启动 Docker 基础设施。
3. 建立独立的集成门禁，使用隔离的真实容器执行适配器测试、黑盒 E2E 和故障演练。

## 最终决定

采用第三种方案：

- 使用独立 Compose Project、宿主机端口和临时数据卷启动 PostgreSQL、Redis、
  Redpanda 以及完整 API；
- 执行现有 PostgreSQL、Redis 和 Kafka 适配器集成测试；
- 从公开 HTTP API 完成注册、登录、幂等下单、支付成功、订单确认和通知成功的黑盒
  E2E；
- 依次停止 Redis、Redpanda 和 PostgreSQL，验证 `/healthz` 继续返回 `200`，而
  `/readyz` 返回 `503`；恢复依赖后验证 readiness 回到 `200`；
- 无论成功或失败都删除本次验收创建的临时容器、网络、数据卷和本地构建镜像；失败时
  先输出依赖与 API 日志；
- CI 中把这一流程放入独立 Integration Job，并让它在基础代码、观测配置和容器构建
  通过后运行。

## 选择原因

- 黑盒 E2E 只依赖公开协议，更容易发现路由、认证、序列化、依赖注入和异步组装问题；
- 适配器测试能提供比 E2E 更精确的事务、锁、幂等和消息语义失败定位；
- 隔离数据卷让重复运行不会消耗开发环境库存，也不会继承旧 Kafka offset；
- 故障演练证明 liveness 和 readiness 的契约在真实依赖故障下成立，而不仅是单元测试
  中的模拟结果。

## 影响和遗留风险

- 集成门禁比单元测试慢，并依赖 Docker、镜像仓库和空闲宿主机端口；
- 当前故障演练验证依赖摘流和恢复，没有模拟网络延迟、丢包、磁盘写满或数据损坏；
- 本地 Redpanda 是 Kafka 协议兼容实现，不能替代真实生产 Kafka 集群的容量与升级验收；
- E2E 使用模拟支付和通知 Provider，不代表真实第三方沙箱已经完成验收。

## 重新评估条件

- 接入真实第三方沙箱时，增加独立合同测试且禁止使用真实资金或真实用户数据；
- 进入生产部署阶段时，增加数据库备份恢复、迁移回滚、容量压测和灰度回滚演练；
- 集成检查耗时显著增长时，按依赖拆分并行 Job，但必须保留完整黑盒链路。
