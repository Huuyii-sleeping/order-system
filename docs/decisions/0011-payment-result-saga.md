# 0011：使用支付结果事件推进订单 Saga

## 背景

订单创建和支付调用属于不同的本地事务。支付成功后如果直接由 Payment Worker
修改订单，两个模块会共享存储接口；拆成服务后也无法用一个数据库事务覆盖支付、
消息 Broker、订单和库存。支付明确失败时，还必须可靠地取消订单并释放预占库存。

## 决策

- Payment Worker 不依赖订单存储。支付进入 `succeeded` 或 `failed` 时，在更新
  Payment、完成 PaymentTask 的同一个本地事务中写入支付结果 Outbox。
- 支付结果使用版本化事件 `payments.succeeded.v1` 和 `payments.failed.v1`，订单 ID
  作为消息 Key。事件只携带订单侧校验所需字段，不暴露渠道引用和原始失败原因。
- `unknown` 表示第三方结果尚不确定，不发布失败事件，也不取消订单。只有明确拒绝
  才发布 `payments.failed.v1`。
- 订单侧消费者在一个本地事务中写 Inbox、锁定订单、校验用户与金额，再执行状态
  转换。成功事件使订单 `pending -> confirmed`；失败事件使订单
  `pending -> cancelled`，并释放该订单预占的库存。
- Inbox、订单状态和库存补偿一起提交。重复投递命中 Inbox 后不会重复释放库存；
  任一业务更新失败时 Inbox 也回滚，使同一消息可以安全重试。

## 一致性语义

这是事件协作式 Saga 的一个步骤，提供最终一致性而不是跨服务 ACID。订单创建、
支付处理和订单收尾通过事件依次推进，当前没有额外保存一张“全局流程状态表”。某个时间窗口内，
支付可能已经成功而订单仍是 `pending`；Outbox Worker 重试后会最终推进订单。链路
仍然是至少一次投递，消费者 Inbox 负责把重复投递转成一次业务效果。

当前订单与支付位于同一个模块化单体和同一个 PostgreSQL 中，但仍通过事件端口交互，
用于保留未来拆分边界。内存模式为订单和支付分别维护 Outbox Worker；PostgreSQL 模式
使用共享 `outbox_messages` 表和一个 Worker。

## 遗留边界

- 当前 Saga 只覆盖单次支付和订单确认/取消，没有退款、人工审核或超时关单。
- 对于支付成功但订单已经进入冲突终态的事件，消费者返回错误并最终进入 DLQ，
  需要告警和人工调查，不能自动把已支付订单改成取消状态。
- Kafka 的消息发布、业务事务和 offset 提交仍有崩溃窗口，不能宣称恰好一次。
