# 灰度发布与回滚运行手册

## 本地演练

执行：

```bash
make rollout-check
```

脚本会：

1. 编译一个不可变的本地 API 二进制；
2. 在 `28082` 启动旧版本进程；
3. 等待旧版本 `/readyz` 通过并检查商品接口；
4. 在 `28083` 启动新版本进程；
5. 等待新版本 `/readyz` 通过；
6. 向新版本发送少量 canary 请求；
7. 停止新版本，模拟发布回滚；
8. 验证旧版本仍能正常响应；
9. 关闭剩余进程并删除临时目录。

脚本只使用内存模式，不会连接现有 PostgreSQL、Redis、Kafka 或 Docker 容器。
端口冲突时可以覆盖：

```bash
ROLLOUT_OLD_PORT=38082 \
ROLLOUT_NEW_PORT=38083 \
make rollout-check
```

## 真实发布检查清单

- 新镜像已经构建并固定 digest；
- 数据库迁移已经完成，并且旧应用仍然兼容；
- 新实例 `/healthz` 和 `/readyz` 均符合预期；
- 灰度流量只发送到 ready 实例；
- 观察 HTTP 5xx、P95、关键业务指标、队列 Lag 和后台 Worker 错误；
- 新版本异常时先停止流量扩大，再回滚应用实例；
- 回滚后确认旧版本继续消费任务，且没有重复扣库存或重复支付；
- 数据损坏时不要直接覆盖活动数据库，进入新库恢复和对账流程。

## 排查顺序

```text
实例是否启动
  → readiness 是否通过
  → HTTP 错误率和 P95 是否异常
  → 数据库/Redis/Broker 是否异常
  → 后台 Worker 是否停止或积压
  → 是否需要停止灰度并回滚应用
```

不要只看进程是否存活。一个进程可以继续返回 `/healthz=200`，但它的数据库连接、消息消费者或后台 Worker 可能已经不可用。
